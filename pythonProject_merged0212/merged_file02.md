# 自动化测试介绍

## 什么是自动化测试

自动化测试是用于提升测试效率的一种手段。

目前整个软件行业，其实对于所有的软件的研发需求，基本已经达到一定量的瓶颈了。绝大部分公司对于自己的产品更多处于维护和升级的阶段，而非新产品的研发阶段。而这也就意味着很多的软件本身是处于稳定状态的，或者它的基础功能处于稳定状态。为此如果要投入人力和精力，将会是极大地消耗和成本的增加。于是行业内部需要有自动化测试的相关辅助。来解决这个问题。于是自动化就成为了市场主流了。

自动化测试技术本身不是用于测试bug的。或者说自动化测试技术的核心不在于bug的测试。

- 自动化功能测试：简称自动化。将手工测试所执行的一部分内容转为机器可以识别的形态，来交由机器去执行测试工作。主要核心目的在于提升测试的效率。让我们有更多的精力和时间去系统其它的部分进行深入测试，找出更多的问题。
- 自动化性能测试：简称性能测试。是对系统效率的测试手段。其目的在于校验系统的效率是否达到预期。

自动化测试永远不能完全替代手工测试。自动化测试一定是优先考虑系统的正向核心业务流程的实现，在这个基础上才会逐步去完善系统的其他自动化测试需求。

## 自动化测试分层

其实就是UI自动化和接口自动化两个方面。科学角度来进行分层结构其实有三层：

- Unit层：单元测试层级。其实就是所谓的单元测试，属于白盒测试阶段。是目前所有的测试手段中颗粒度最小的测试应用。但是对于测试人员没有意义。一般是由开发人员来完成。主要手段是code review，交叉评审等手段来实现。一般不会交由测试人员来专职完成白盒测试。属于三层级别的塔尖位置。
- Service层：从测试的维度而言，就是接口测试层级。其实就是所谓的接口测试。一般而言由开发和测试一同完成。接口测试也是目前市场最核心需要的一种测试手段。如果你想要快速找工作。接口测试必然要优先掌握。也是目前测试人员必须掌握的核心技术之一。
- UI层：最底层的分层，所有一切都是基于系统的页面来实现的自动化测试。整个层级中颗粒度最大的一个层级。UI层自动化是最接近用户实际使用操作的一种层级。

## 自动化测试介入

所有同学请记住，无论你的公司要不要求自动化，你都必须要去做。不是为了公司负责，是为你自己负责。

- 需要从0开始搭建自动化测试体系的公司：
  - 自动化测试推行成功的标志是这个公司的相关人员都在使用你的自动化。
    - 离不开团队的需求
    - 离不开公司的需求
    - 离不开公司发展的需求
  - 自动化测试的结构定义
  - 基于项目提取自动化测试的内容。
  - 实现框架。进行测试用例的编写。
  - 培训。让相关人员都用起来。
  - 跟进框架的优化和维护。
  - 持续的推广和维护。
  - 一定要一个领导来支持你。而且是能有一锤定音的能力的领导。
- 已有自动化测试，但是需要你来维护和管理的公司：
  - 熟悉现有的自动化测试技术。
  - 基于现状，结合你自己的能力来实现框架的功能优化。让实际的自动化测试开展变得更加轻松。

自动化测试在什么时间介入（执行）：

1. 不是所有的项目都适合自动化测试
   1. UI自动化测试开展，一般是在冒烟测试阶段和后期回归测试阶段下的业务流程的执行
   2. 接口自动化测试开展，只需要后端接口逻辑实现，即可开展接口自动化测试。
2. 不是每一个功能或者模块或者流程都需要自动化。一定优先考虑核心业务流程的正向业务实现。

所有一次性的项目不要考虑投入从零开始的自动化。

# 元素定位

## HTML标签

所有的Web系统，所谓的前端，其实就是HTML和JS。前端其实也就是人肉眼可见的界面。无论页面长啥样，所有一切的内容都是基于元素的形态来实现展示的。不同的元素其实就是一个个不同的HTML的标签。

HTML本身是一种标记语言。整体的结构是基于树状结构栏来实现的。所有的标签都是有自己的父级和子级节点存在，基于整个页面的结构来决定。

所有的标签都是基于三个部分来组成的。标签名、标签属性、标签文本。每一个元素不是必须要有完整的三部分。

1. 标签名：决定了元素的类型或者内容。常见的标签：a、input、div、span。。。。。。
   1. 任何元素在获取和操作时，只基于标签名来决定是否可行。其余一切都不重要。
2. 标签属性：可以有多个属性存在。不同的属性之间通过空格来进行分离。属性赋值通过=来进行。所有的属性都是包含在<>之中的。在标签名之后的。属性本身是可以有值也可以无值。
3. 标签文本：在元素的尖括号以外的内容。一般常见于超链接，span等标签之中。文本是可有可无的。
4. 标签模板：<标签名称 属性1="value" 属性2="value2">标签文本</标签名称>或者<标签名称 属性1="value" 属性2="value2"/>

日常在网站里看到的所有内容，是由不同的元素来组成的。不同元素的样式大多数时候都是基于元素的class属性来决定的。而且元素本身的内容也是基于标签内容来决定。所以眼见不一定为实。一切都以HTML的内容作为决定。至于说页面长啥样，这是前端决定的，不是测试需要考虑的问题。

1. id

3. classname
4. tagname

# 三类等待

## 等待的作用

等待是自动化中非常常用的一种手段。所有的浏览器在页面加载元素的过程中，是需要有时间的。但是自动化程序执行的过程是不会有暂停或者考虑时间等待的问题的。所以有时候代码出现报错，但又有时候可以正常运行，一般就是因为等待时间的设置有问题。

所以为了确保自动化测试流程的执行稳定性。所以必须在程序之中设置合理的等待机制。确保代码运行的时候，必要条件下可以适当进行等待处理。

在自动化的技术领域内，稳定性一定是在效率之上的。

## 三类等待机制

### 强制等待

也就是说代码执行到强制等待时，无论在做什么，都必须停下来。等到时间结束为止，再继续运行后续的内容。是使用sleep()方法实现强制等待。sleep本身属于是time库下的一个方法。你可以通过time.sleep()或者sleep()都可以。区别在于你导包的目标是库还是函数。需要传入一个参数，单位为秒。

强制等待一般是新手在学习阶段下，以及特定的场景进行调试时会选择使用的一种手段。

优点：简单使用。学习成本非常低。

缺点：冗余高。浪费不必要的时间。

### 隐式等待

其实就是一种driver对象的设置项。设置driver的全局等待时间。本身对于driver的整个生命周期有效。在每一个操作的时候，都会进入到隐式等待，一旦能够正常操作，则继续进行后的代码执行。所以隐式等待设置的是最大等待时间，而不是固定等待时间。如果等待时间达到最大值后，依旧没有找到元素，则代码会继续往后运行。

优点：只需要一行代码，可以全局生效。而且只要找到目标则立即执行，不会有多余的等待时间

缺点：一旦出现找不到元素的时候，就会持续等待，一定程度上会直接影响到程序的运行效率。

### 显式等待

专门针对元素进行的等待机制。类似于强制等待。只有当代码运行到显式等待的代码的时候，才会进入等待的状态。一旦等待时间结束，还未找到对应的元素，则会抛出超时异常。显式等待的两种等待机制（两种机制完全相反，搞懂一种，另一种自然就明白）：

1. until：一直到条件满足为止
2. until_not：一直到条件不满足为止

优点：专门针对某一个特定的元素等待的最有效方式。直接粗暴。效率会很高

缺点：语法结构相对复杂。而且类似于强制等待，如果使用太多则会有较高的代码冗余。

<br/>

隐式等待和显式等待是可以共用的。强制等待虽然用的少，但是在特定场景下还是很好用的。隐式和显式在官网中有建议不要一起使用。但是在实际应用的过程中目前一切正常。

## 页面加载策略

Selenium默认是等待页面所有内容全部加载完成以后才会执行后续的代码。但实际页面的加载策略是可以修改的。

在Selenium中对页面加载策略进行修改需要调用options

页面加载策略在修改之前我们需要先确认，当前系统能否支持策略的修改。因为修改加载策略意味着有很多的请求在还未执行时，我们就开始执行我们的自动化操作了。所以容易导致系统出现不可预知的问题。

# 断言与JS执行器

## 断言

在所有的自动化测试过程中一定会有断言的存在。因为所有的自动化测试技术还是为了测试而服务的。在所有的测试行为上，都会有一个叫做预期结果和实际结果的对比。用于判断本次测试行为是否通过。在自动化测试中，这个对比结果的行为就是所谓断言。

在ui自动化测试中，断言一般是针对流程的结束行为来进行断言的。在断言的时候，我们会选择最具有代表性的内容来进行断言校验。通过这个断言来判断整个流程执行的正确性。

1. 页面中存有多个可以用于断言的点，自行选取一个即可。
2. 所有的数据都是我们在测试之前已经预先准备好的，所以预期结果在执行之前我们就已经知道了。

在ui自动化中，断言其实就是选取指定元素的文本，或者判断页面中某个特定元素是否存在即可。

## Document对象与JS执行器

JS执行器是解决UI自动化领域疑难杂症的一把好手。要实现JS执行器的调用，一定要先明白js的核心对象，document。

- document对象：前端技术中核心对象之一，所有的页面元素，也就是所谓的HTML的内容，其实都可以基于document对象来进行对应的操作行为，类似于元素获取，点击，属性修改等等等等。

# DDT+Yaml数据驱动实现

## DDT应用与原理

数据驱动是用于管理复杂的数据情况而实现的一种数据管理手段。如果是简单的数据，直接可以写入代码之中，没有必要为了数据驱动而做数据驱动。

ddt全称叫做Data Driver Test，数据驱动测试模块。ddt本身只做简单数据的管理。复杂数据不基于ddt管理。但是可以通过ddt导入。ddt属于第三方模块。所以需要通过pip install ddt的指令来进行安装。

ddt在UnitTest中的使用是基于装饰器的形态来实现的。

## Yaml语法结构与基本应用

yaml是一种文件格式。一般常用于自动化测试数据管理和系统程序的配置文件进行使用。所有后缀名为yaml、yml的文件，都是yaml文件。它属于一种非常灵活轻便的文件。具备有自己的格式要求。

常规的测试数据，从文件读取之后一般都是需要做数据处理的。但是yaml则不需要。因为yaml可以直接实现int和str的明确区分，以及直接传入list或者dict数据格式的内容。极大地减少了有关于数据管理的行为。可以让整个测试过程更加简单。

yaml的安装需要通过pip install pyyaml来实现。

### 语法规则

yaml本身是一种对缩进非常敏感的语法结构。所有的数据内容和上下级关系都是基于缩进来进行控制和管理。就类似于Python

1. list格式的数据一定是- 的结构来实现的，一定记得在-后面有一个空格存在。
2. 默认情况下所有的数字都为int类型，如果想要在yaml中将数字变为str，则记得在数字上添加一组引号。
3. dict格式的数据一定是key: value的结构来实现的，一定记得在key:后面有一个空格的存在
4. 字典和list是可以相互嵌套的，前提条件是你需要注意yaml文件的语法结构规则即可。

## Yaml锚点与引用

锚点其实就是类似于变量的概念。我们可以提取yaml中的公共部分的内容，作为锚点，在后续其他组数据的编写过程中，通过引用锚点的方式将重复的数据引入。让整个yaml的数据结构可以变得更加精简。

语法规范：

- 锚点：通过用&来定义。
- 引用： 通过*锚点名称来进行 锚点的引用
- 追加：通过<<来进行内容的追加

# POM设计模式

## POM原理介绍

POM，简称PO，全称叫做PageObject Model，页面对象模型。是一种专门用于做UI自动化测试的设计模式。只能用于UI自动化测试领域。也是业内最佳的一种设计模式。

关键字驱动设计模式，是一种能够基于一个框架实现对多种不同业务的自动化测试实现的效果。POM，是一种专门针对单个系统进行量身定制的设计模式。是以一对一的形态来解决单个系统的UI自动化测试的设计模式。

一定记得，合适的技术才是最优方案。

POM虽然是单独实现一对一系统的自动化测试，但是具备有优秀的维护能力和测试的覆盖率，能够极大程度下满足系统的深度和广度的测试效果。

传统的测试思维：

1. 我要实现登录到修改个人信息的业务流程
   1. 访问登录url，进入登录页
   2. 输入账号，输入密码，点击登录按钮
   3. 跳转登录成功
   4. 点击个人信息页
   5. 点击修改
   6. 输入修改数据
   7. 点击保存按钮
   8. 断言是否修改保存成功。

POM的设计思路：

1. 访问登录页
2. 执行登录流程
3. 访问个人信息页
4. 执行修改信息流程
5. 断言校验修改是否成功

POM的设计思路上，相较于传统的测试思路，更加注重的是页面和流程。而传统测试思路注重的是业务和操作步骤。

POM其实就是关注业务流程本身，将核心业务流拆分为基于页面对象所实现的不同子业务流，将子业务流程拼接之后，就实现了一个完整的核心业务流程。

在UI测试的过程中，我们所关注的一定是一个个不同的核心业务流。而不同的业务流程都是基于子流程来实现的。不同的页面恰恰对应了不同的子流程。所以POM其实就是基于不同的流程来拆分不同的页面。基于页面拆分不同的子流程。最终通过子流程的拼接实现核心业务流程的执行，从而实现自动化测试的业务流程的完整性。在过程中不再去关注单个元素的操作和执行，目标全部定义在流程上。

## POM设计思路

POM核心结构，其实就是四层（所有其他的层级基本都是基于这四层来实现的）

1. 基类：类似于关键字驱动类。是自动化测试的底层逻辑，主要用于封装各类的操作行为
2. 页面对象层：POM的核心。用于封装不同的页面，页面中包含有核心的操作元素和操作业务。
3. 测试用例层：测试代码，用于管理和实现自动化测试
4. 测试数据层：用于管理测试过程中的数据内容。

# Fixture应用

## 什么是Fixture

Fixture，夹具。在pytest之中，通过Fixture来实现对用例的前置和后置的内容的完成。除此之外，还可以基于Fixture实现更多其他预置内容的定义，以函数的形态实现。

## Fixture基本应用

```
Fixture的基本应用：
        1. Fixture的基本示例：
            1. 前期的环境准备，数据准备。测试的预置工作。
            2. 测试行为的执行。（基于测试用例实现各类测试操作）
                在pytest中，我们可以把常规重复执行的测试行为提取为函数的形态。定义为Fixture，通过Fixture的调用实现预置流程的调用
                通过这种方法，可以极大简化测试用例的内容。提升代码的维护性。降低冗余。
            3. 基于预期结果来对测试行为进行校验
            4. 释放资源
        2. Fixture的基本应用：
            1. Fixture都是基于函数的形态存在的。通过装饰器来进行定义。
            2. Fixture的调用，是通过对用例进行入参的定义。来传入Fixture进行调用。
            3. Fixture可以通过return将需要的内容返回。在用例中通过调用入参的名称实现对return对象的操作。
            4. Fixture可以在单个用例中一次性调用多个不同的Fixture来满足用例的执行条件。
            5. fixture本身一般是定义在conftest.py文件之中。如果不在conftest中定义Fixture，而是在用例文件定义
                则Fixture的有效范围只存在于当前py文件中。其余py文件无法调用。(conftest.py定义后同级和子文件可以使用)
'''
```

## Fixture运行机制

```
fixture运行机制：
        1. 缓存机制。在用例执行的过程中，Fixture可以被多次调用。在第一次请求之后，如果有返回值，则会通过
            这一个返回值来执行后续的所有操作。而不是重新运行。
        2. 因为Fixture本身其实就是函数。如果需要调用Fixture所生成的值，则必须添加return。否则返回None
        3. Fixture本身是属于自定义函数的范畴。所以会有一定的概率出现报错的情况。当Fixture出现错误的时候
            或者说当执行测试用例时，所关联调用的Fixture出现错误时，程序直接终止运行，测试用例的内容不会执行
            并返回为error状态。(执行顺序是先执行调用的fixtrue，若在调用时就报错则终止运行)
        4. Fixture的执行，必须要在用例中调用了，才会运行。
        5. Fixture提供有autouse参数。默认为False。如果修改为True，可以实现每一个用例在执行的时候都会默认调用
            该Fixture。如果说你的Fixture中需要定义return值，则不推荐使用autouse。(以为需要先调用，才能获取返回值)因为多此一举
            所以autouse虽然可以方便我们实现对Fixture的调用。但仅限于没有return的Fixture。

```

# 接口基础

## 接口原理讲解

接口，API。提供应用程序与开发人员进行访问交互的一组案例程序的能力。案例程序



前端：肉眼可见的所有内容，比如UI界面等，都属于前端

后端：服务端。代码的逻辑处理，数据生成等等等等。实现软件的逻辑运算的功能。

接口属于后端。前端所有发送的数据，都会传递至服务端的接口部分，进行处理。

<br/>

后端的结构其实就是底层逻辑与接口的组合。接口本身不做任何的逻辑操作。主要用于接收数据，调用逻辑，再生成数据返回至前端。

<br/>

足浴城——软件系统

朋友——系统用户

大堂经理——传递数据，网络协议

技师部门——计算的位置，生成结果，接口

技师——生成的最终结果数据

<br/>

系统的接口本身属于相对封闭的内容。早期的系统是没有所谓明确的接口定义和概念的。因为没有前后端分离。

系统通过接口实现对后端的访问。也就意味着接口就是后端的门。前端获取用户数据，基于网络协议发送至后端的接口，由接口实现逻辑代码的调用与结果的运算和生成。返回数据至前端。让用户可以直观看到。接口一定会有返回值。

```python
def login_interface(data):
  result = login(data)
  return result
```

接口测试属于黑盒测试领域：

接口属于后端，不需要有任何的界面，也不需要关联到前端。只属于后端逻辑的调用。所以接口在测试的时候，是不需要有前端的介入的。接口测试完全不依赖前端。直接通过对后端的访问，实现整个测试的内容。接口测试属于黑盒测试领域。整个测试也就是接口的调用，然后校验返回结果是否满足预期。

接口就是直接对后端逻辑代码进行测试的行为。不关前端的事情。在实际测试的过程中，相较于UI测试而言，会更加深入一些。

永远不要认为你的系统只有正常人会访问。前端会设置有非常多的限制。要求后端也要做同样的限制。

为什么现在企业对于接口测试非常看重？

1. 接口测试本身属于后端的测试行为，可以很好地保障后端的质量。
2. 可以一定程度地保障系统的安全性。
3. 可以更好地满足企业的研发需求。（版本迭代多，由于以下改变多：界面 交互 新需求）
   1. 接口本身的修改相对而言是很少的，接口一直处于相对稳定的状态。所以维护成本极低。
   2. 满足测试前移的需求。接口测试的目的是保障后端服务的质量，不需要前端的介入。
4. 可以极大缩短研发周期，提升代码的研发过程中的质量。

接口测试的核心：接口本身是接收数据的。并进行数据的处理，返回结果的过程。所以我们的测试关注点就在于如何设计测试数据。以及如何校验返回的结果是通过还是不通过。

接口测试是性能测试的开始。

## 内部接口与外部接口

系统的两种接口：

1. 内部接口
   1. 系统内部由开发人员自主研发的接口。
2. 外部接口
   1. 直接通过调用第三方系统已经实现的接口，比如支付，第三方登录等。

我们在实际的测试行为中，只关注内部接口的测试。而外部接口，我们只需要调用即可。不需要测试。

一般而言，第三方接口会有沙箱或者其他的mock版本。如果说没有提供，你可以选择自己做一个mock

# HTTP网络协议

## HTTP网络协议介绍

当你启动一个浏览器，访问一个url的时候，你的浏览器到底经历了几个步骤？

1. 浏览器会进行url的解析（解析出ip地址）
2. 建立TCP临时连接通道。
3. 数据的发送
4. 服务端基于对应的接口进行数据的接收并处理计算。
5. 生成结果并原路返回。关闭临时通道
6. 返回数据的接收，解析。
7. 前端页面的渲染

HTTP网络协议属于应用层的协议。底层还是基于TCP来实现的。目前市场最主流的就是HTTP网络协议。主流版本是HTTP1.1。现阶段https可以基于http2.0来实现通信，而http只能通过http1.1来实现通信。HTTP网络协议被称作目前人机交互效率最高的一种网络协议。

HTTP网络协议主要包含有HTTP和HTTPS两种协议：（HTTPS性能，效率比http差，因为ssl加密	）

1. 两者没有什么区别。HTTPS就是HTTP+SSL证书。在安全性上会优于HTTP
2. 虽然HTTPS安全性更高。但是很少会有使用HTTPS的情况。
3. 区分HTTP和HTTPS，最有效的方式就是通过url来判断。

<br/>

URL：

- 网站、地址、链接等相关称呼。正确称呼叫做统一资源定位符。类似于XPATH。用处就是用来访问不同的接口。
- 网络协议://IP:PORT/Path?args1=xxx&args2=aaa
- https://www.baidu.com/s?wd=huangcaica&rsv_spt=1&rsv_iqid=0x942c22f8005690a6&issp=1&f=8&rsv_bp=1&rsv_idx=2&ie=utf-8&tn=baiduhome_pg&rsv_dl=tb&rsv_enter=1&rsv_sug3=11&rsv_sug1=2&rsv_sug7=100&rsv_sug2=0&rsv_btype=i&inputT=1509&rsv_sug4=2087
- https默认端口是443 http默认端口是80
- path就是接口的路径
- url后面不会有任何参数存在。

## 请求与响应详解

### 请求 request

用户端下发到服务端的内容，叫做请求。也就是request

一个请求总体分为三个内容：

1. 请求行
   1. 请求方法：不同的接口有不同的请求方法，在请求接口时，必须请求方法与接口规定的保持一致。所有接口的请求方法都在接口文档中有明确定义。直接参考即可。
      1. Get：一般用于数据展示。不会涉及到任何新增、修改校验等关联功能的操作行为。(用于查询)
         1. 默认会将所有的参数都明文显示在url后方，通过?进行拼接，多参数间通过&关联。
         2. 请求的长度有限制（因为url有长度限制。）
         3. 安全系数相较于post更低。
         4. 数据可以被缓存（历史搜索记录）
      2. Post：一般用于表单的提交、数据的修改和新增
         1. 不会将参数明文在url后方显示。而是放在请求体中。
         2. 请求长度没有限制（因为所有数据都在请求体，而非url中）
         3. 相对安全系数高于Get请求
         4. 无法被缓存
   2. url：显示本次请求的接口。
   3. 版本信息：显示当前是基于哪一个HTTP的版本来进行数据传递的。
2. 请求头（request headers）
   1. 用于通知服务端，客户请求的数据格式以及规范。
   2. 用于添加额外的数据内容
   3. KEEP ALIVE：长连接，HTTP1.1默认存在的设置参数。
      1. TCP临时通道不再是一次性的了。在创建之后会持续保持，等到空闲一定时间后再销毁。
3. 请求体（request body）
   1. 仓库。用于存放传输的参数（数据加密属于前端技术。与请求没有关系。）

### 响应（每个接口都会有响应）

服务端生成的结果叫做响应结果，Response。

响应三个部分：

1. 响应行：
   1. 版本信息
   2. 响应状态码：status code。表示本次请求的运行结果（只与请求本身的流程有关，与业务无关。）
      1. 100，一般看不到。表示请求已经被接收，正在继续处理中。
      2. 200，表示请求成功，响应已正常返回
      3. 301，表示重定向，当前请求的资源转移到另外一处。
      4. 404，路径错误，一般指访问的接口路径不存在。可能是我们自己接口path写错了。也可能是开发人员没有部署该接口。
      5. 500，服务器内部异常
2. 响应头（response headers）
   1. 与请求头类似。定义格式和规范
   2. 告知客户端如何处理特定的数据内容（set-cookie）
3. 响应体（response body）
   1. 响应结果文本信息的存放位置。（接口测试中的断言点。）

## Cookie、Session、Token

HTTP网络协议是无状态网络协议。每一个请求都是独立的存在个体。彼此之间不会有任何关联。

Cookie：本地保存的文件。以kv（键值对）对格式保存的所有的缓存信息。用于服务端和请求头信息的添加

Session：临时会话。不同用户访问系统会生成不同的临时会话窗体。所有用户与系统的交互都是基于这个窗体来实现的。session会话全部都是由服务器来进行管理的。不同的session会话会由不同的SessionId来进行管理。sessionid由系统生成，存放在用户的cookie之中。session管理起来会比较的麻烦和复杂。

Token：身份令牌。用户在得到系统的授权之后。就会获得由系统生成的token令牌。保存在本地的cookie之中。每一次请求时都带上token。服务端对接收的token进行判断和处理。即可识别业务的关联。（加密，本地不储存）

<br/>

在实际的接口测试过程中，接口关联业务的测试行为，是接口测试最为核心的部分。而接口关联就是基于这些内容来实现的。通过sessionid或者是token这类的数据实现接口关联的执行，通过A接口生成的数据，作为B接口的参数，实现AB接口的关联。（接口关联是核心，解决http无状态问题）

      1. get：一般是用在数据的展示。不会涉及到任何的关于数据的修改、校验、新增等操作
         1. 所有的参数都是明文显示在url的后方。通过?进行链接。（也可以将参数不明文显示）
         2. 请求的长度是有限制的。（其实是URL有长度限制。而不是get请求本身。）
         3. 安全系数相对较低
         4. 数据可以被缓存
      2. post：一般用于表格的提交。数据的修改和新增
         1. 参数不会明文显示在url后方。而是放在body之中。
         2. 长度没有限制。（因为数据存放在body之中）
         3. 安全系数相对更高
         4. 无法被缓存
   2. url：显示本次请求的接口url
   3. 版本信息：显示当前是基于哪一个版本的http协议来进行的数据传输
2. 请求头：request headers
   1. 用于通知服务端，请求的数据格式以及规范。
   2. 用于添加额外的数据。一般而言额外数据都是自动添加的。
   3. keep-alive：http1.1的时候才有的设置。长连接，核心是通道
      1. 将原本一次性的tcp临时链接通道转为长期通道。可以持续保持下去。只要用户在继续与系统交互。则该通道一直存在，否则销毁。
      2. 长连接和无状态没有任何关系。
3. 请求体：request body
   1. 仓库。用来保存本次请求需要传递的数据。（数据加密一般是前端的操作。和请求体没有关系。）

### 响应

服务端返回至用户端的数据结果。叫做响应。response。

响应分为三个部分：

1. 响应行：
   1. 版本信息
   2. 响应状态码：status code。用于表示本次请求的运行结果（只与请求本身有关，与业务无关。）
      1. 100，基本看不到。表示请求已被接收，正在继续处理中。
      2. 200，表示成功，响应已经返回。
      3. 301，表示重定向，当前请求的资源转移到了另外一处。
      4. 404，表示访问的接口路径不存在。要么是调用接口是url写错了。要么是指向的服务未部署
      5. 500，服务器内部异常。
2. 响应头：response headers
   1. 与请求头类似，定义规范和格式
   2. 告知客户端如何处理特定的数据
      1. Set-Cookie表示用户端本地保存至cookie文件之中。
3.  响应体：response body
   1. 生成的响应结果保存位置。（响应结果一般都是文本的格式。一般在接口测试阶段，断言的内容就是这一块。）

<br/>

## Cookie、Session、Token

HTTP网络协议是无状态协议。

### cookie

cookie本身是一个本地文件。用于管理和存储各个网站的相关内容的。整体内容是基于键值对kv形态来进行管理。可以存放指定的服务端和响应头信息。

### Session

临时会话机制。不同的用户在访问系统的时候会生成不同的会话框。该用户的所有交互和数据传递都是基于该Seesion会话框来进行管理的。session会话都是基于服务端来进行管理的。不同的会话框有不同的独立id信息。也就是SessionId。服务端管理会话，将sessionid传递至对应用户本地，保存在cookie之中。用户请求时，带上sessionid即可让服务器识别具体的会话框。每次用户请求时基于sessionid来作为鉴权的手段。

### Token

临时身份令牌。用户获得系统授权之后，系统返回一个token令牌。保存在本地cookie之中。后续的每一次请求都会带上token值。通过对token值的校验来判断你是否授权。

## 数据加密与解密

很多系统为了确保用户数据的安全性，所以在数据传输时，会通过加密数据的形态来实现数据的传输。所有数据在传输至接口之前，会基于前端来实现一次数据加密，然后将加密的数据传递至服务端，进行后续的逻辑处理。从而避免了用户数据被窃取时是明文状态的情况。

# 面试技巧

## 面试流程

- 面试前
  - 查看公司的招聘信息，了解公司具体的招聘岗位需求是什么。以便于更好去准备这一次的面试。
  - 查看公司的本身信息。出于安全考虑，避免不必要的麻烦。熟悉公司的核心产品信息。
  - 个人的装扮，素雅大方得体即可。
  - 把缺失的技能，能够补足的基础知识好好补足一下。
- 面试中
  - 面试记得提前到
  - 笔试是可以抄资料的，如果遇到不会的，大方拿手机看资料。
  - 面试流程：自我介绍——聊项目——聊技术——聊薪资——提问——结束
    - 自我介绍
      - 可以提前准备，但是不要死记硬背
      - 介绍内容挑重点说，时间控制在三分钟以内。
      - 突出你个人的经历、学历、擅长的技术能力等相关方面，参与过的厉害的项目之类的内容。都可以聊
    - 聊项目：面试官感兴趣的项目
      - 介绍项目本身的背景和核心业务
      - 着重讲解个人在项目中实际参与的测试工作内容
    - 技术交流：基于项目和你聊相关的技术内容，以及通过技术内容发散更多的内容
      - 你会的技术
        - 结合你的实际业务来进行技术的详细讲解
      - 你不会的技术
        - 完全没有接触过的技术，就直接说我不会。
        - 如果是某个点的技术你不会，可以通过平替来进行技术的讲解
      - 一定要搞清楚面试官的问题。他到底想要知道什么？（如果摸不透，可以再次询问一下）
    - 聊薪资：不要和任何人比较
      - 明确你自己的薪资目标
      - 薪资是基于整体面试的过程来评估的。
      - 大方谈，不要害羞。
    - 提问：
      - 一定要提问
      - 通用提问模板：
        - 贵公司研发团队规模如何，测试团队规模如何
        - 如果入职贵公司，我主要负责的工作核心内容是什么
        - 围绕产品进行针对性的提问
      - 雷区避免：
        - 贵公司加班多不多
        - 是不是有拖欠工资
        - 有投诉，有劳动纠纷
        - 五险一金是不是正常缴纳
        - 贵公司的产品是什么
  - 面试注意点：
    - 面试是一种双向选择的合作协议形态。不需要太过于卑微了。
    - 面试的时候不要太过于随意。还是稍微端着点。
    - 沟通过程中一定记住声音保持在相对平稳的状态，不要忽大忽小。也不要过大过小。
- 面试后
  - 自我总结，避免在后续的面试中犯同样的错误。不要拿特例当做常规。
  - 到了约定时间，如果对方没有联系你，记得主动询问一下。
    - 如果面试不通过，起码你知道不通过的原因在哪里。

## 面试心理学

1. 所有面试的小花招都是附加值，核心在于面试时你的实力表现。
2. 所有问题一定要清楚了，听懂了再回答，保持彼此的沟通效率和氛围。
3. 沟通时避免口头禅和语气用词。同时避免过于结巴。
4. 学会观察
5. 不要背诵任何内容。
6. 主动权的夺取：面试过程中谁提问谁有主动权。学会适当的夺取主动权，但是分人而异。
